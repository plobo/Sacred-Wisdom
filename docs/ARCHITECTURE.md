# Sacred Wisdom — Architecture Notes

Spec: `requirments/IMPLEMENTATION_PLAN.md`. This file records decisions (spec §14 rule 20).

## Project
- Generated by **XcodeGen** from `project.yml`; run `xcodegen generate` after adding/removing files.
  The `.xcodeproj` is a build artifact of `project.yml`.
- Swift 6 language mode, strict concurrency `complete`, iOS 17.0 deployment target.
- Targets: `SacredWisdom` (app), `SacredWisdomTests` (Swift Testing: unit + integration),
  `SacredWisdomUITests` (XCTest UI).

## Layers (dependencies point inward)
```
Features (Views + @Observable @MainActor ViewModels)
   └─> Domain UseCases ──> Domain Repository protocols <── Data repositories
App/AppDependencies (composition root) wires concrete Data types into use cases and vends ViewModels.
```
- Views hold no business logic; they render a ViewModel `State` enum (idle/loading/loaded/failed).
- Repositories and use cases are `Sendable` protocols with `async throws(AppError)` (typed errors).
- `AppCoordinator` owns the selected tab and one `[AppRoute]` stack per tab.
- `AppConfiguration` reads launch arguments (`-ui-testing` skips the splash).

## Content
- Scripture is never in Swift source. `Resources/Database/sample_library.json` is a **content package**
  (schema v2, normalized: sources, collections, translations, books, sections, passages). At launch it is
  imported into SQLite; the app reads only from SQLite (`SQLiteScriptureRepository`).
- `SampleLibraryRepository` reads a package directly in memory. It backs unit tests and is the reference
  implementation: `ScriptureRepositoryContractTests` run every behaviour against both implementations.
- The JSON is **generated**, never hand-edited: `python3 -I tools/content/build_sample_library.py <cache-dir> <out.json>`.
  The script downloads each source and extracts text verbatim; the only normalizations (footnote markers,
  line-wrap joins, Macauliffe's pre-punctuation spaces, Gutenberg `--` → em dash) are listed in its docstring.
- `SampleLibraryIndex` validates every reference (religion, collection, translation, book, section, source,
  duplicate IDs, default translation). An invalid library throws `contentCorrupted`; nothing partial is shown.
- If bundled content fails to load, `UnavailableLibraryRepository` is injected so the UI shows an error state.
- Test fixtures use obviously synthetic text (`[fixture text]`) and are never presented as scripture.

`passage_texts` rather than one `translated_text` column, because passages have several translations. Stable passage IDs are translation-independent
(`bible.matthew.5.9`). Each passage carries its texts with the collection's default translation first.

## Database (SQLite + FTS5)
- System `SQLite3` library; no third-party dependency. `SQLiteConnection` is an actor that owns the handle,
  so all SQL is serialized. Foreign keys on; WAL for the file database.
- File: `Application Support/SacredWisdom/scripture.sqlite`, excluded from backup (it is rebuilt from packages).
  UI tests (`-ui-testing`) use an in-memory database.
- `DatabaseManager` opens → migrates → imports bundled packages, lazily on first query, once. Concurrent first
  callers share one initialization; a failure is not cached, so the error screen's retry works.
- **Migrations** (`ScriptureSchema`): ordered, tracked in `PRAGMA user_version`, each in a transaction with its
  version bump. A database newer than the app is refused. Never edit a shipped migration; append one.
  - v1: `religions`, `content_sources`, `scripture_collections`, `translations`, `scripture_books`,
    `scripture_sections`, `scripture_passages` (+ precomputed `reading_order`), `passage_texts`, `content_packages`.
  - v2: `passage_search` FTS5 table, one row per passage × translation, indexing original text, translation,
    book title, section title and reference; `unicode61 remove_diacritics 2` tokenizer.
- **Import** (`ContentImporter`): SHA-256 of the package decides whether to import. Validation reuses
  `SampleLibraryIndex`; the import is one transaction that replaces every collection the package owns
  (cascading to texts) and its FTS rows. A package cannot overwrite another package's collection.
- **Full-text search** (`FullTextSearchIndex`): every user term is quoted before MATCH, so FTS operators in user
  input are inert. Modes: all terms, or exact phrase. Optional religion filter; results ordered by bm25.
  Phase 4 builds query normalization, ranking and filters on top of this.
- v3: search columns store **folded** text (`SearchTextNormalizer`: Arabic harakat/Quranic marks/tatweel removed,
  alef variants unified; Hebrew points/cantillation removed, maqaf and sof pasuq become spaces; lowercased).
  The migration clears the index and package records, so the next launch re-imports. Display text is never folded.

## Universal search (Phase 4)
```
input ─▶ SearchQueryParser ─▶ SearchQuery ─▶ CombinedSearchRepository ─▶ SearchScriptureUseCase ─▶ grouped results
          (normalize, quotes      (clauses)      primary: LocalKeywordSearchRepository (FTS5)     (by tradition,
           → phrase, stop words,                 supplementary: [] (semantic, later; failures      fixed order)
           prefix ≥ 3 chars)                      are ignored so keyword search always works)
```
- **Modes:** keywords (all must match, prefix-matched), exact phrase in straight or curly quotes, or both.
  Stop words are dropped only when other words remain ("What is said about mercy?" → `mercy*`).
- **Ranking:** weighted bm25 (reference ×3, text ×1, titles ×0.4). Passages matching every clause come first;
  if fewer than 10, passages matching any clause follow (`matchedAllTerms == false`; the UI says so).
- **One result per passage.** It ranks by its best translation hit; the preview uses the collection's default
  translation when that matched, otherwise the matching one ("gentle" → World English Bible).
- **Filters** (`SearchFilters`): religion (chips), language and translation (sheet), collection (API only:
  one collection per tradition today). Language matches a collection's original language or a translation's.
- **Groups follow the fixed tradition order**, not relevance, so no tradition is ranked above another.
- **Preview:** translation text verbatim, matched words bolded via attributes only; the original script is also
  shown (in its own direction) when the query matched it.
- **History:** SwiftData `SearchHistoryEntry` (user data store, separate from scripture). Recorded on explicit
  search only (Search key, suggestion, recent), de-duplicated on folded text, capped at 20. In-memory for UI tests;
  if the store cannot open, search works and history is empty.
- **Suggestions:** neutral suggested questions, each guaranteed by a test to return passages; type-ahead
  completions from recent searches and suggestions.
- Voice search (spec Screen 5) arrives with the Speech framework in Phase 6.

## Verse details, favorites and user data (Phase 5)

- **Verse Details** (`Features/PassageDetail`) shows the reference, original text, *every* translation (matched,
  preferred or default first), attribution for each source shown, structural context (collection, book, section,
  position, original language, themes), related passages, the user's note, and Share/Bookmark. Search results,
  related passages, Favorites and the reader's ⓘ button open it; "Read in Context" opens the reader.
- **No generated commentary.** "Explanation/context" is limited to facts from the collection's own structure.
  Commentary will appear only when it comes from a verified, attributed source.
- **Related passages = editorial themes.** I tried keyword overlap on the real corpus, and it linked passages on
  words like "never", "called" and "hast", which would mislead. Instead, content packages (schema v3) carry
  `themes` and per-passage theme IDs. `build_sample_library.py` records, for each tag, the word in the passage's
  own translation text that justifies it, and the build fails if that word is missing. Links are only across
  traditions, ranked by number of shared themes, then tradition order, then reading order. The UI labels them
  "linked by shared editorial themes" and names the shared theme on each card. Schema v2 packages still load,
  with no themes.
- **Migration v4** adds `themes` (shared across packages, like religions) and `passage_themes`. Links cascade
  with their passage and are re-imported every time; clearing `content_packages` forces existing installs to re-import once.
- **User data lives only in SwiftData** (`UserBookmark`, `UserCollection`, `ReadingHistoryEntry`,
  `SearchHistoryEntry`), and refers to scripture only by stable passage ID. A bookmark whose passage is no longer
  installed is shown as "Passage unavailable", never silently dropped.
  - Notes live on the bookmark, as in the spec's model. Saving a note bookmarks the passage; an empty note clears
    the note and keeps the bookmark; removing a bookmark that has a note asks first.
  - Reading history keeps one row per passage (the latest view), capped at 100. Both the reader and Verse Details
    record it. Settings → Clear Reading History removes it.
  - Collections are deduplicated ignoring case and spacing. Deleting a collection keeps its bookmarks, unfiled.
- **Change propagation:** `UserDataChanges` holds revision counters. View models bump them after writing, and
  screens use `.task(id:)` to reload (Favorites, Home recents, an open detail or reader, search bookmark icons).
- **Persistence locations:** production uses SwiftData's default store. UI tests use memory, unless
  `-ui-testing-user-data-store <name>` names a store in the app's temporary directory (with optional
  `-ui-testing-reset-user-data`), which lets a UI test relaunch the app and check persistence.
- **Sharing** (`PassageShareFormatter`) shares the original and translation verbatim, with reference, translation
  name, and every source's attribution and license (Tanzil permits only verbatim copies, with credit).
- **Deferred:** editing translation preferences from details, iCloud sync. (Audio arrived in Phase 10.)

## Siri, Shortcuts and voice input (Phase 6)

- **App Intents only**, with no custom SiriKit. The intents in `App/Intents` are thin: each calls
  `ScriptureIntentService` (`Services/Intents`), which doesn't use the AppIntents framework and is unit tested
  against the real library.
- **Intents:**

  | Intent | Opens app? | Returns |
  |---|---|---|
  | `SearchScriptureIntent` | no | Spoken reference list (one per tradition, at most 3) + `[PassageEntity]` |
  | `OpenSearchResultsIntent` ("Search Holy Books") | yes | Search tab with results |
  | `AskQuestionIntent` | no | Concise answer quoting the best passage from up to 3 traditions, verbatim with references |
  | `FindVersesAboutTopicIntent` | no | Same answer, for a `ScriptureTopic` |
  | `OpenPassageIntent` | yes | Verse Details on the Home tab |
  | `DailyVerseIntent` | no | Today's passage, quoted with translation name |
  | `OpenDailyPassageIntent` ("Open Daily Scripture") | yes | Today's Verse Details |

- **No generated text before Phase 7.** Answers are assembled only from retrieved passages, and a test checks that
  every quotation is a complete, verbatim database text. When nothing matches, the answer says so: the spec's
  "forgiveness" example has no passage in the sample library.
- **Phrases:** App Shortcut phrases can't contain free text, so "Ask Sacred Wisdom" makes Siri ask for the
  question. Topic phrases ("Find verses about peace in Sacred Wisdom", "Ask Sacred Wisdom about mercy") use the
  `ScriptureTopic` AppEnum. A test checks that every topic except forgiveness finds passages. Guidance searches
  "path" and truth searches "true", the words the texts actually use.
- **Shared state:** `AppSession.shared` holds the one `AppDependencies` and `AppCoordinator` used by both the UI
  and intents. Opening intents call `coordinator.openPassage(_:)` or `showSearchResults(for:)`; the Search tab
  consumes `pendingSearch` once.
- **Voice search** (`Services/Speech`, `VoiceSearchSheet`) is separate from Siri. `SpeechRecognitionService` is a
  protocol. `AppleSpeechRecognitionService` uses `SFSpeechAudioBufferRecognitionRequest` with
  `requiresOnDeviceRecognition = true`, so audio never leaves the device. If there's no on-device model for the
  language, voice search says so rather than falling back to the server. Listening stops after 60 s. The audio tap
  and result handler are built in `nonisolated` functions so they don't inherit main-actor isolation.
- **UI tests** never touch the microphone: under `-ui-testing` a `ScriptedSpeechRecognitionService` is used
  (`-ui-testing-speech "<words>"`, `-ui-testing-speech-denied`; with neither, it reports "unsupported").
- **Limits:** Siri itself can't be driven from tests. Verification is the intent service tests, running the real
  intents' `perform()` in the test host, and checking `Metadata.appintents` (7 intents, 1 entity, 1 enum,
  5 shortcuts). The live recognizer needs a check on a real device.

## AI question assistant (Phase 7)

- **Retrieval first** (`AnswerQuestionUseCase`):
  1. Local search finds verified passages. This needs no AI, and a search failure is the only error that fails a question.
  2. The best passages, interleaved across traditions (best of each first, at most 8, each truncated to 700 chars
     for the prompt only), become the AI's numbered context.
  3. If AI is off, unavailable, fails, or produces nothing verifiable, the passages are shown unchanged with a
     short note. With no passages, the AI is never called.
- **`ScriptureAIService`** (spec §8 signature, typed throws), with these implementations:
  - `FoundationModelsScriptureAIService`: iOS 26 on-device model behind `#if canImport` and `#available`, guided
    generation (`@Generable` explanation + cited passage numbers), temperature 0.2.
  - `RemoteScriptureAIService` over a `RemoteAIProvider` protocol (JSON reply). This is the abstraction for
    OpenRouter-style providers. No concrete provider ships, and the app still makes no network requests.
  - `UnavailableScriptureAIService`, and `ScriptedScriptureAIService` for tests.
- **Shared prompt rules** (`ScriptureAIPrompt`): use only the numbered passages, cite as [n], don't quote words not
  in a passage, name no other references, stay neutral and brief, don't rank traditions or present interpretation as fact.
- **`AIResponseValidator`** runs on every reply, sentence by sentence (NLTokenizer). It removes any sentence that:
  - cites a number outside the context,
  - quotes (double or curly quotes) text that isn't a contiguous span of a provided passage (case, diacritics and
    punctuation ignored), or
  - names a chapter:verse reference outside the context.

  If nothing remains, or nothing cites a provided passage, the whole explanation is withheld. Removed sentences
  are counted and disclosed in the UI. Output is capped at 1,500 characters.
- **Display:** passages come only from the database, grouped by tradition, each with "View Full Passage". The
  explanation sits in a separate dashed card labeled "AI-generated explanation · <provider>", with Sources links
  ([n] → Verse Details) and a note that interpretations differ.
- **AI is optional:** Settings → AI Explanations (UserDefaults, on by default; in memory under UI testing).
  Search, Siri intents and Verse Details never use AI. Siri's Ask stays quote-only.
- **Verified on this machine:** the simulator reports the system model *available*, but generation fails because
  the model assets aren't installed. The live test therefore exercises the fallback. Real generation needs a
  device with Apple Intelligence enabled.

## Offline downloads (Phase 8)

- **Packages** (`content/packages/`, built by `tools/content/build_download_packages.py` from the Phase 2 source
  cache with the same verbatim rules and no network access):

  | Package | Contents | Translations |
  |---|---|---|
  | `bhagavad-gita-ch2` | 72 verses, Sanskrit + Besant | Speaker headings as printed |
  | `bible-matthew-5` | 48 verses, KJV | WEB only for 5:3–10, the part already cached |
  | `dhammapada-ch1` | 20 verses, Pali | Sujato + Müller |

  The builder asserts that every passage in the bundled sample comes out byte-identical, so IDs, bookmarks, notes,
  history and theme links carry over. Each package is a normal schema-3 content package holding exactly one
  collection, with `availability: downloaded`.
- **Manifest** (`manifest.json`): §10's fields (id, collectionID, version, languages, fileSize, sources, license,
  sha256, schemaVersion) plus title, passageCount and a relative path. `ContentManifest.decode` rejects:
  - bad IDs, checksums or sizes (over 50 MB);
  - unsupported schemas;
  - path traversal or absolute paths;
  - duplicate IDs.
- **Hosting:** the `CONTENT_MANIFEST_URL` build setting goes into Info.plist as `SWContentManifestURL`
  (`SacredWisdom/App/Info.plist`, merged with the generated plist). Only https is accepted. It is empty for now, so
  the screen says no content server is configured. To publish, upload `content/packages/` and set the URL.
- **Pipeline:**
  1. `URLSessionPackageTransport` downloads with progress and pauses with resume data
     (`cancelByProducingResumeData`, where the server supports it), and maps connectivity errors to "offline".
  2. `PackageInstaller.verify` checks exact size, SHA-256, decodes and runs `SampleLibraryIndex`, checks the
     schema matches, and checks the collections are exactly `[collectionID]`.
  3. `PackageFileStore` writes atomically to `Application Support/SacredWisdom/Packages/<id>.json` plus
     `<id>.entry.json`, which is the metadata for offline listing. The folder is excluded from backup.
  4. `DatabaseManager.installDownloadedPackage` imports it, and the files are removed again if that fails.

  Nothing is stored or imported unless every check passes.
- **Ownership (migration v5 adds `content_packages.role`):**
  - A downloaded package supersedes the bundled package's collection.
  - A bundled re-import (for example after an app update) skips collections owned by a download.
  - Two downloads claiming one collection is a conflict.
  - `removeDownloadedPackage` deletes the package and force re-imports the bundled sample, so removal restores
    the sample.
- **Offline:** at launch the database imports bundled packages, then every package file on disk. Files that fail
  are skipped so the library still opens. Reading, search, favorites and history never touch the network.
  Without a connection or server, the Offline Content screen lists installed packages, which can still be removed.
- **Storage:** Settings → Offline Content shows the database file size (with WAL/SHM), package bytes and the
  total, plus per-package size and license.
- **Network scope:** `URLSessionPackageTransport` is the only networking in the app. It fetches only the
  configured manifest and packages and sends no user data, only a generic User-Agent.
- **Tests:** packages are served from the repository via file:// URLs, which use the real URLSession transport.
  `SacredWisdom/Tests/Fixtures/tampered-packages` holds the Dhammapada package with "hatred" → "HATRED" (same
  length) under the original checksum. Regenerate it after rebuilding packages with:
  `python3 -I -c` *(copy `dhammapada-ch1.json`, replace the first b"hatred" with b"HATRED", write the original
  manifest entry)*.
  Under UI testing the packages folder is cleared at launch unless `-ui-testing-keep-packages` is passed.

## Polish and release (Phase 9)

- **Settings (Screen 10):**
  - Appearance (System / Light / Dark, applied with `preferredColorScheme`).
  - Scripture text size: a multiplier on Dynamic Type, shared with the reader's text-size menu.
  - Per-collection preferred translation.
  - Offline Content, AI Explanations, Clear Reading History.
  - Sources & Licenses, which lists every source with attribution, license and link.

  Display preferences live in `AppPreferences`, translation choices in `UserDefaultsTranslationPreferenceStore`
  (UserDefaults; under UI testing a volatile suite emptied at launch). "Preferred language" is not offered:
  every installed translation is English, so it would change nothing.
- **Accessibility:**
  - Color tokens meet WCAG AA (4.5:1) on every background in both appearances. Light gold became 0x856119.
    Tradition tints share one contrast level per appearance (light about 5.6:1, dark about 7.4:1) so no tradition
    stands out. Text on purple fills uses `onPrimary`. `ColorContrastTests` checks all of this exactly.
  - Emblems and icons use `@ScaledMetric`. Labels wrap instead of truncating. Text-block labels stack at
    accessibility sizes. The reader's bottom bar shows icons only at those sizes and is capped at
    `accessibility2`. Small controls have 44 pt targets. The text-size value is part of the stepper's visible label.
  - `AccessibilityAuditUITests` runs Xcode's audit on 13 screens in light mode, dark mode and the largest
    accessibility text size, with zero findings allowed for element detection, hit regions, descriptions,
    traits, actions and parent/child structure. These are excluded or skipped, and the skipped ones are listed
    in the test log:
    - Contrast, Dynamic Type and clipping audits: excluded. The pixel-sampling audit flagged text measured at
      16:1 and labels that weren't clipped (grouped VoiceOver elements, content under translucent bars).
      Contrast is enforced by the unit test; Dynamic Type and clipping were reviewed on largest-size screenshots.
    - Issues on elements covered by the floating system bars, and the system search field's clear button.
    - Element-detection warnings that name no element. Two remain: the Reader and Al-Fatihah's Verse Details.
      Six candidate causes were removed one at a time without effect (toolbar, bottom bar, footer, original
      text, letter-shaped icons, title).
- **Right-to-left:** `View.scriptureDirection(_:)` lays each scripture block out in its own language's direction.
  Arabic and Hebrew run right to left; English, Sanskrit, Pali and Gurmukhi run left to right, even inside a
  right-to-left interface. Reviewed with `-AppleLanguages (ar) -NSForceRightToLeftWritingDirection YES`.
- **Search performance:** `SearchPerformanceTests` (XCTest `measure`) uses a synthetic 12,000-passage,
  24,000-text corpus of filler, never shown as scripture. A broad term matching about 60% of texts takes about
  80–95 ms per search on the simulator. Batching result passages (`passages(ids:)`, 2 queries instead of about
  200) made no measurable difference; FTS5 bm25 ranking dominates. Budget: 4 searches under 1 s.
  `LaunchPerformanceUITests` measures cold launch.
- **Error handling:** `Log` (OSLog) records failures by category (database, userData, downloads, ai, speech).
  It never logs scripture, notes, questions or queries. Recent-search clear and remove failures are now shown
  to the user instead of being swallowed.
- **Release:**
  - Privacy manifest: `SacredWisdom/Resources/PrivacyInfo.xcprivacy` (no tracking, no collected data; reasons
    CA92.1 and C617.1).
  - App icon: generated by `tools/appstore/make_app_icon.swift`.
  - Screenshots (6.9-inch, light and dark): generated by `AppStoreScreenshotTests`, which is skipped unless
    `TEST_RUNNER_SW_APPSTORE_SCREENSHOTS=1`.
  - Listing, privacy answers and review notes: `AppStore/metadata.md`.
  - The Release configuration builds for device (unsigned) and simulator. Signing needs a development team.

## Audio and text-to-speech (Phase 10, spec §11)
- **Abstraction:** `AudioService` (`Domain/Repositories/AudioService.swift`), `@MainActor`, one request at a time;
  a new request stops the previous one, whose handler gets `.superseded`. Implementations:
  `SystemSpeechAudioService` (AVSpeechSynthesizer, on device), `RecordedAudioService` (AVAudioPlayer for licensed
  files), `RoutingAudioService` (sends recordings and text to the right one; the only source of `.superseded`, so a
  request is told once) and `ScriptedAudioService` (silent; unit tests drive it with `emit`, UI tests use a 2 s
  self-playing mode). The app has a single service, so only one passage plays at a time.
- **What may be heard:** `ResolveAudioTrackUseCase`. A licensed recording from `RecordedAudioCatalog` wins (the app
  ships `EmptyRecordedAudioCatalog`: no recordings are licensed yet). Otherwise the translation is synthesized only
  if `AudioLicensePolicy` permits its source license: public domain, CC0, CC BY, CC BY-SA. ND, NC and anything
  unrecognized are refused, and the player says why. Every bundled and downloadable translation qualifies
  (`AudioIntegrationTests`). The spoken text is the verified text, only trimmed.
- **Originals are never synthesized.** Synthetic recitation of the Quran or Gurbani would misrepresent how they are
  recited, Tanzil forbids altering the text, and devices have no Sanskrit, Pali or Gurmukhi voices. Originals can
  come later as licensed recordings through the catalog.
- **Labeling:** synthesized audio is captioned "<translation>, system voice", so it is never taken for a recording.
- **`AudioPlaybackController`** (`Features/Shared`, one per screen): status (idle/unavailable/ready/playing/paused/
  finished/failed), progress, speed, voices. Speed and voice are fixed once an utterance starts, so changing them
  restarts at the current word (`wordStart`). A change made while paused applies on resume.
- **Screens:** `AudioPlayerBar` sits above the reader's navigation bar and at the bottom of verse details. It has
  play/pause, progress, a speed menu (0.75–1.5×), a voice menu (installed voices for the language, best quality and
  the user's region first, novelty and Personal Voices excluded) and, in details, which translation to hear. The
  reader keeps listening when you move between passages. With "Continue to Next Passage" on (the default) it
  advances when a passage finishes. Leaving a screen stops its audio, so nothing plays without controls.
- **Preferences** (`AppPreferences`): speed, continuous playback, voice per base language. Settings has a
  Listening section.
- **Audio session:** `.playback` / `.spokenAudio` (heard with the silent switch on). It is deactivated with
  `notifyOthersOnDeactivation`. Interruptions pause playback and show it as paused. There is no background-audio
  mode, since playback stops when its screen goes away.
- **UI testing:** the scripted service is used, and `-ui-testing-audio-no-voice` simulates a device with no voice.
- **Not verified here:** real voices on device (simulator voices vary). The AVSpeechSynthesizer path is covered by
  its helpers (`wordStart`, `rate`). `RecordedAudioService` is tested end to end with a generated tone file.

## Reader
- `ReaderViewModel` shows one passage; previous/next follow reading order across sections and books
  within a collection (`ScriptureRepository.adjacentPassageID`).
- Translation choice is remembered per collection by `TranslationPreferenceStore`
  (in-memory actor now; SwiftData `UserPreferences` later). If a passage lacks the chosen translation,
  it falls back to the default while keeping the choice.
- Original text: larger serif, gold-accented block labeled "Original · <language>", laid out RTL for
  Arabic/Hebrew. Translation: plain card labeled "Translation · <name>". Attribution footer on every passage.
- Font size: 0.8×–1.8× multiplier on `@ScaledMetric` sizes, so Dynamic Type still applies.

## Design system (`Core/DesignSystem`)
- `SWColors`: semantic tokens with light/dark variants; per-tradition tints of similar luminance.
- `SWTypography`: serif headings and scripture, built on Dynamic Type text styles.
- `SWSpacing`, `SWRadius`; components: `SWCard`, `ReligionCard`, `PassageCard`, `SectionHeader`,
  `SearchBarButton`, `Loading/Empty/ErrorStateView`, `PlaceholderFeatureView`.
- Tradition emblems are Unicode glyphs with U+FE0E appended to force text (not emoji) presentation,
  so all six render identically.

## Accessibility identifiers
`screen.<name>`, `tab.<name>`, `home.<section>`, `religionCard.<religionID>`,
`passageCard.<passageID>`, `section.<sectionID>`, `reader.*`, `state.loading|empty|error`.
Apply an identifier to a container only together with `.accessibilityElement(children: .contain)`;
otherwise SwiftUI propagates it over the identifiers of every child.
